# seo Specification

> Seeded from code on 2026-10-20 (lab-2876, LAB-2923/LAB-2924); correct me.
> Site-wide rules for what search engines may index and under which address. Page-specific rules live in their own specs (`job-board`, `profiles`, `teams`).

## Purpose

Which addresses of the site search engines are told to index, and how every other address points them there: sitemap entries, canonical addresses, permanent redirects and `noindex` pages.

## Requirements

### Requirement: The sitemap lists only addresses meant to be indexed

`/sitemap.xml` SHALL list each page under the address it is indexed at. It SHALL NOT list an address that redirects. The events calendar is listed as `/events/all` and the Demo Day landing page as `/demoday`.

#### Scenario: Static entries

- **GIVEN** the sitemap is generated
- **WHEN** a crawler reads it
- **THEN** it lists `/events/all` and `/demoday`
- **AND** it does not list `/events`

#### Scenario: Browse index pages

- **GIVEN** the team browse index has 6 pages
- **WHEN** the sitemap is generated
- **THEN** the static pages section lists `/teams/browse` and `/teams/browse?page=2` to `/teams/browse?page=6`, and every page of the member and project indexes the same way
- **AND** when the API can't be read, it still lists page 1 of each index

#### Scenario: Teams hidden from signed-out visitors

- **GIVEN** the directory API serves `GET /v1/teams/crawl-index`
- **WHEN** the sitemap is generated
- **THEN** it lists the teams of the crawl index
- **AND** it does not list a team at access level `L0`, whose profile answers 404 to a crawler

#### Scenario: API without a team crawl index

- **GIVEN** `GET /v1/teams/crawl-index` fails
- **WHEN** the sitemap is generated
- **THEN** it lists the teams of the full team list, as before

#### Scenario: Empty member profiles

- **GIVEN** the directory API serves `GET /v1/members/crawl-index`
- **WHEN** the sitemap is generated
- **THEN** it lists the members of the crawl index
- **AND** it does not list a member with no photo and no bio text, whose profile is `noindex`

#### Scenario: API without a member crawl index

- **GIVEN** `GET /v1/members/crawl-index` fails
- **WHEN** the sitemap is generated
- **THEN** it lists the members of the full member list, as before

### Requirement: Empty member profiles are not indexed

A member profile with no photo and no bio text SHALL have `robots` `noindex, follow` (LAB-3096). Bio text is the bio with HTML, entities and the AI bio notices ("Bio is AI generated…", "Bio is generated by Husky AI…") removed. Any photo, or bio text of any length, SHALL leave the profile indexable: Search Console showed member pages with short or AI-written bios getting impressions, so bio length is not a bar. The rule SHALL match the API's member crawl index (`utils/member-indexing.ts` mirrors the backend's `member-crawl-index.ts`), and the browse index SHALL list only crawl-index members.

#### Scenario: Profile with no photo and an AI notice only

- **GIVEN** a member with no photo whose bio is only "Bio is AI generated & may not be accurate."
- **WHEN** a crawler reads the profile's metadata
- **THEN** `robots` is `noindex, follow`

#### Scenario: Profile with a photo and no bio

- **GIVEN** a member with a photo and no bio
- **WHEN** a crawler reads the profile's metadata
- **THEN** the profile has no `robots` restriction

### Requirement: The sitemap is an index of per-section sitemaps

`/sitemap.xml` SHALL be a sitemap index (`<sitemapindex>`) listing one sitemap per section, at absolute addresses: static pages, teams, members, projects and jobs (`/sitemaps/sitemap/<section>.xml`). Each section sitemap SHALL list only its own kind of page. robots.txt SHALL keep naming `/sitemap.xml`. The sitemap index, the section sitemaps and robots.txt SHALL NOT be answered with session cookie headers.

#### Scenario: Crawler reads the sitemap

- **WHEN** a crawler requests `/sitemap.xml`
- **THEN** it receives a sitemap index with five `<sitemap>` entries
- **AND** each entry's sitemap lists only static pages, teams, members, projects or jobs

#### Scenario: No session headers on crawler files

- **WHEN** a client requests `/sitemap.xml`, a section sitemap or `/robots.txt`
- **THEN** the response has no `Set-Cookie` header

### Requirement: The old host's addresses have their own sitemap during the domain move

`directory.plnetwork.io` answers every path with a 301 to the same path on `os.pl.xyz` (a Cloudflare rule). Until Search Console shows the move complete, production (`APPLICATION_BASE_URL` `https://os.pl.xyz`) SHALL serve `/sitemaps/legacy-directory-plnetwork.xml`: every address the section sitemaps list, the root `/` and the old homepage `/home`, on the old host, each once and with no `lastmod`. It is submitted in Search Console by hand; Google accepts it because one account has verified both hosts. `/sitemap.xml` and robots.txt SHALL NOT name it. Every other deployment SHALL answer it with 404, since its entity ids are not the old host's. It SHALL NOT be answered with session cookie headers.

#### Scenario: Crawler reads the old host's sitemap on production

- **GIVEN** the team sitemap lists `https://os.pl.xyz/teams/T`
- **WHEN** a crawler requests `https://os.pl.xyz/sitemaps/legacy-directory-plnetwork.xml`
- **THEN** it lists `https://directory.plnetwork.io/teams/T`, `https://directory.plnetwork.io/` and `https://directory.plnetwork.io/home`
- **AND** it lists no `os.pl.xyz` address and no `lastmod`

#### Scenario: Feature env

- **WHEN** a client requests `/sitemaps/legacy-directory-plnetwork.xml` on `directory-portal-lab-<n>.os.pl.xyz`
- **THEN** the response is 404

### Requirement: The homepage is the site root

The homepage SHALL render at `/`, and its canonical address, its `WebSite` JSON-LD and the pages sitemap SHALL name the site root (`https://os.pl.xyz/` on production). `/home`, the homepage's address until LAB-3255, SHALL redirect permanently (308) to `/`, keeping its query string, so old links, digest emails and notifications (`/home?news=<uid>`, `/home?view=news`, `/home#login`) open the same view. In-app links to the homepage, and the navigation's check for "already on Home", SHALL use `/`. A notification whose link says `/home` SHALL match the homepage.

#### Scenario: Crawler on the site root

- **WHEN** a crawler requests `https://os.pl.xyz/`
- **THEN** the response is 200 with the homepage
- **AND** its canonical address is the site root, `https://os.pl.xyz` (written without the trailing slash, the same address)

#### Scenario: Old homepage link

- **GIVEN** a link to `/home?news=N`
- **WHEN** a visitor or a crawler requests it
- **THEN** the response is a 308 redirect to `/?news=N`

#### Scenario: Notification sent before the move

- **GIVEN** an unread notification whose link is `/home?news=N`
- **WHEN** the member opens `/?news=N`
- **THEN** the notification is marked read

### Requirement: One address for the events calendar

`/events` SHALL redirect permanently (308) to `/events/all`, and `/events/all` SHALL declare itself as its canonical address. Other pages under `/events/` SHALL NOT redirect.

#### Scenario: Old events address

- **GIVEN** a link to `/events`
- **WHEN** a visitor or a crawler requests it
- **THEN** the response is a 308 redirect to `/events/all`

#### Scenario: Calendar canonical

- **WHEN** a crawler requests `/events/all`
- **THEN** its canonical address is `/events/all`

### Requirement: Demo Day landing canonical

The Demo Day landing page SHALL declare `/demoday` as its canonical address. Pages under `/demoday/` SHALL NOT inherit that canonical.

#### Scenario: Landing page

- **WHEN** a crawler requests `/demoday`
- **THEN** its canonical address is `/demoday`

### Requirement: The sign-up flow is not indexed

Every page under `/sign-up` SHALL be marked `noindex, follow`, whatever its query string.

#### Scenario: Sign-up with a return address

- **WHEN** a crawler requests `/sign-up?returnTo=/members/M`
- **THEN** the page carries `<meta name="robots" content="noindex, follow">`

### Requirement: Non-production deployments are not indexed

Every response SHALL carry `X-Robots-Tag: noindex, nofollow`, whatever host serves it, when the build is a Vercel preview (`VERCEL_ENV=preview`) or was built with `SEO_NOINDEX=true` (the k8s feature envs). Any other build SHALL send no `X-Robots-Tag` of its own. That includes production, local development, a build with neither variable set, and any other `SEO_NOINDEX` value. robots.txt SHALL NOT block the crawl, so crawlers can see the header.

#### Scenario: Preview on a custom domain

- **WHEN** a crawler requests `/` on `pr-<n>.preview.dev.os.pl.xyz`
- **THEN** the response carries `X-Robots-Tag: noindex, nofollow`

#### Scenario: Feature env

- **WHEN** a crawler requests `/` on `directory-portal-lab-<n>.os.pl.xyz`, deployed with `SEO_NOINDEX=true`
- **THEN** the response carries `X-Robots-Tag: noindex, nofollow`

#### Scenario: Production

- **WHEN** a crawler requests `/` on `os.pl.xyz`
- **THEN** the response carries no `X-Robots-Tag`

### Requirement: Main pages name the searches they should be found for

The home page, members, teams, projects, the events calendar, the job board and the Demo Day landing page SHALL each have a title and a description of their own, and no two of them SHALL share either. Each SHALL name "Protocol Labs". The home page SHALL also name "innovation network", and Demo Day SHALL name "venture investors" and "VC". The job board keeps the title "Protocol Labs Jobs | LabOS".

#### Scenario: Home page

- **WHEN** a crawler requests `/`
- **THEN** its title and description both contain "Protocol Labs" and "innovation network"

#### Scenario: Demo Day

- **WHEN** a crawler requests `/demoday`
- **THEN** its title and description both contain "venture investors" and "VC"

### Requirement: Every page has one h1

Each page SHALL have exactly one `<h1>` element in its server-rendered HTML. A page that renders a separate copy of its title for narrow screens SHALL make that copy a heading by role (`role="heading" aria-level="1"`) or hide it from assistive technology, not a second `<h1>`. A job posting's own `h1` and `h2` SHALL render as `h3`, under the role page's `h1` (the role title) and `h2` ("About the role"), and so SHALL the `h1` and `h2` in a team's, member's or project's own description.

#### Scenario: Listing and profile pages

- **WHEN** a crawler requests `/members`, `/teams`, `/projects`, `/jobs`, a team profile or a project profile
- **THEN** the HTML has one `<h1>`

#### Scenario: Job posting with h1 sections

- **GIVEN** a role whose description has `<h1>The Role</h1>`
- **WHEN** a crawler requests the role page
- **THEN** the HTML has one `<h1>`, the role title, and "The Role" is an `<h3>`

### Requirement: The home page says what the network is

With `NEXT_PUBLIC_SHOW_HOME_V2` off, `/` SHALL have the `<h1>` "Protocol Labs Directory", visually hidden so the top of the page keeps its design, and read by assistive technology. For a signed-out visitor, the page SHALL show a definition of the Protocol Labs network and the directory, of 40 to 60 words, as visible text in an "About" section at the foot of the page.

With the flag on, the signed-out `/` SHALL have one visible `<h1>`, the mission "Protocol Labs drives breakthroughs in computing to push humanity forward.", The visible sentence under it SHALL say what the network is ("We are an innovation network that connects over 760 tech startups, …"), and the Join the network card beside it SHALL say what the directory is for. The page SHALL have no About foot.

In both cases, the definition SHALL NOT be hidden from view, because text shown only to crawlers is hidden text.

#### Scenario: Crawler on the home page

- **GIVEN** the flag is off
- **WHEN** a crawler requests `/` without cookies
- **THEN** the HTML has one `<h1>`, "Protocol Labs Directory"
- **AND** the definition is in a visible "About Protocol Labs Directory" section after the focus areas

#### Scenario: Visitor on the home page

- **GIVEN** the flag is off
- **WHEN** a signed-out visitor opens `/`
- **THEN** the top of the page starts with the welcome card, as before LAB-3089
- **AND** the definition appears at the foot of the page

#### Scenario: Crawler on the new home page

- **GIVEN** the flag is on
- **WHEN** a crawler requests `/` without cookies
- **THEN** the HTML has one `<h1>`, the mission sentence, with the definition right under it
- **AND** the Organization and WebSite JSON-LD are still present

### Requirement: The home page names Protocol Labs as structured data

`/` SHALL carry JSON-LD with an `Organization` (Protocol Labs, with `sameAs` links to protocol.ai, Wikidata Q63930216, X, LinkedIn and YouTube) and a `WebSite` (Protocol Labs Directory, at the home page's canonical address) published by it.

#### Scenario: Home page markup

- **WHEN** a crawler requests `/`
- **THEN** the HTML has an `application/ld+json` script with the `Organization` and the `WebSite`

### Requirement: Profiles carry entity structured data

Member, team and project profiles SHALL carry JSON-LD built only from what a signed-out visitor sees on the page, with a `BreadcrumbList` from the section to the profile:

- a member profile: a `ProfilePage` whose `mainEntity` is a `Person` (name, image, job title, the team they work for, bio, skills). Social links and location are hidden from signed-out visitors, so they are not in the markup;
- a team profile: an `Organization` (name, logo, description, and as `sameAs` the contact links the page shows);
- a project profile: a `CreativeWork` (name, logo, tagline, its maintaining team as `creator`, and its links as `sameAs`).

#### Scenario: Signed-out member profile

- **WHEN** a crawler requests a member profile
- **THEN** the HTML has a `ProfilePage` about the member's `Person` and a `BreadcrumbList` Members → member
- **AND** the markup has none of the member's social links or location

#### Scenario: Team contact link that is only a guess

- **WHEN** a team's LinkedIn value is not a handle or address, so the page links to a LinkedIn search
- **THEN** the team's `sameAs` leaves that link out

#### Scenario: Profile text that contains a script tag

- **WHEN** a profile's name or text contains `</script>`
- **THEN** the JSON-LD escapes it and the script element is not ended early

### Requirement: Pages declare their language

Every page's `<html>` element SHALL have `lang="en"` (LAB-3253).

#### Scenario: Any page

- **WHEN** a client requests any page
- **THEN** the response's `<html>` element has `lang="en"`

### Requirement: Links reach every profile

`/members`, `/teams` and `/projects` SHALL each link, in their server HTML, to a browse index at `/<listing>/browse`. The link SHALL be a quiet, visible line under the list, reachable with Tab, and SHALL NOT sit in the listing's toolbar (LAB-3184 found it beside "Sort by"). It was hidden for LAB-3184; Search Console then still called `/teams/browse` "unknown to Google", so it is visible again. The index SHALL list every profile the sitemap lists for that listing, A to Z, 200 per page, as plain links, with links to every page of the index. Each page SHALL have a self-canonical; page 1 SHALL have no `?page=`. A `?page=` that is not a whole number from 1 up, or is past the last page, SHALL answer 404.

The server HTML of every page SHALL link to the pages of each nav dropdown: `/members`, `/teams` and `/projects` from "Directory", and the internal pages of "More" (the events pages among them). Base UI mounts a dropdown's content only while it is open, so each dropdown SHALL also render its internal links as a plain list that is `hidden`: not on screen and not in the accessibility tree (LAB-3253). Links to other sites SHALL be left out of that list.

#### Scenario: Crawler reads any page

- **WHEN** a crawler reads the server HTML of any page, a profile included
- **THEN** it finds `<a href>` links to `/members`, `/teams` and `/projects`
- **AND** a member sees no change in the nav

#### Scenario: Crawler follows links only

- **WHEN** a crawler starts at `/teams`, `/members` or `/projects` and follows only `<a href>` links
- **THEN** it reaches every team, member and project profile in the sitemap

#### Scenario: Member opens a listing

- **WHEN** a member opens `/teams`, `/members` or `/projects`
- **THEN** a "Browse all <listing>, A–Z" link shows under the list, not in the toolbar

#### Scenario: Page past the end

- **WHEN** a client requests `/teams/browse?page=99` and there are fewer pages
- **THEN** the response status is 404

#### Scenario: Teams and contributors on a project page

- **WHEN** a crawler reads a project profile
- **THEN** its maintaining team, contributing teams and contributors are `<a href>` links to their profiles

### Requirement: Sitemap entries carry only what Google reads

`/sitemap.xml` entries SHALL carry `loc` and, where known, `lastmod`, and no `changefreq` or `priority`. A profile's `lastmod` SHALL be its `updatedAt`. A job opening's `lastmod` SHALL be the `lastModified` the API's job crawl index gives (the posting's own date); a job without one SHALL have no `lastmod`, never the nightly sync time. robots.txt SHALL have no `Host:` line.

#### Scenario: Job synced last night, posted in October

- **GIVEN** a job whose crawl-index entry has `updatedAt` from last night's sync and `lastModified` 2026-10-01
- **WHEN** the sitemap is generated
- **THEN** the job's `lastmod` is 2026-10-01 and the entry has no `changefreq` or `priority`

### Requirement: Share cards match the search result

On those pages, `og:title`, `og:description`, `twitter:title` and `twitter:description` SHALL equal the page's title and description.

#### Scenario: A listing page is shared

- **WHEN** a link to `/members` is shared
- **THEN** the card's title and description are the page's own title and description

### Requirement: Demo Day dashboards are not indexed

Pages under a Demo Day (`/demoday/<id>/…`) SHALL be marked `noindex, follow`; they are dashboards for its admins, founders and investors. The event's landing page (`/demoday/<id>`) and its completed view (`/demoday/<id>/completed`) SHALL be indexable, each with its own address as canonical.

#### Scenario: Investor dashboard

- **WHEN** a crawler requests `/demoday/<id>/investor`
- **THEN** the page is marked `noindex, follow`

#### Scenario: Completed view

- **WHEN** a crawler requests `/demoday/<id>/completed`
- **THEN** the page is indexable and its canonical address is `/demoday/<id>/completed`

### Requirement: Canonical addresses have one slash after the host

Every canonical address SHALL be the page's path on the site's base URL, with exactly one slash between them, whether or not the configured base URL ends in "/".

#### Scenario: Base URL with a trailing slash

- **GIVEN** the base URL is configured as `https://os.pl.xyz/`
- **WHEN** a crawler requests `/teams/T`
- **THEN** its canonical address is `https://os.pl.xyz/teams/T`

### Requirement: Public Demo Day pages are in the server HTML

The first HTML response for a Demo Day's landing page (`/demoday/<id>`) and its completed view (`/demoday/<id>/completed`) SHALL contain the page's content, readable without running JavaScript: the Demo Day's name and description, and on the completed view each presenting team's name with a link to `/teams/<uid>`. It SHALL NOT be a loading skeleton. The server HTML SHALL hydrate without a mismatch.

#### Scenario: Completed view, fetched without JavaScript

- **GIVEN** a Demo Day whose status is completed
- **WHEN** a client without cookies requests `/demoday/<id>/completed` and reads the HTML without running scripts
- **THEN** the HTML contains the Demo Day's name as its `<h1>` and its description
- **AND** the HTML lists the participating teams, each with an `<a href="/teams/<uid>">` link

#### Scenario: Landing page of a Demo Day that is not finished, fetched without JavaScript

- **GIVEN** a Demo Day that is open for registration or active
- **WHEN** a client without cookies requests `/demoday/<id>`
- **THEN** the HTML contains the Demo Day's name as its `<h1>`, its description and its date

#### Scenario: Signed-in investor or founder

- **WHEN** a signed-in investor or founder opens the same pages
- **THEN** they are redirected and shown their views as before

### Requirement: An unknown Demo Day is a 404

A Demo Day page whose id the API reports as not found SHALL answer HTTP 404 with the not-found page, for the landing page and the completed view. Any other API failure SHALL keep the page as it was, so an outage never tells crawlers a live Demo Day is gone.

#### Scenario: Unknown id

- **WHEN** a crawler requests `/demoday/<unknown-id>` or `/demoday/<unknown-id>/completed`
- **THEN** the response status is 404 and the page is marked `noindex`

#### Scenario: API outage

- **GIVEN** the Demo Day API answers with an error other than 404
- **WHEN** a visitor requests `/demoday/<id>`
- **THEN** the page does not answer 404
